# AP_Ranging — dev notes

UWB two-way-ranging (TWR) between flying nodes. Reports raw range (meters) to
each peer node; does **not** solve for position. Derived from AP_Beacon, with
the fixed-anchor positioning, fence/trilateration, and vendor/SITL backends
stripped out.

## Hardware reset / pin wiring (crazyflie2) — the `id=0` fix

Symptom: `RNG_TYPE=1` reported `DW1000: not detected (id=0x00000000)`.
Root cause: the Loco deck's RSTn/IRQ are on the deck TX1/RX1 pads = PC10/PC11,
which the hwdef had assigned to USART3 (SERIAL1). PC10 as `USART3_TX` idles high
but pulses LOW on every telemetry byte; RSTn is active-low, so UART traffic was
continuously resetting the DW1000 -> MISO stuck low -> id reads 0. We also never
performed the required power-on reset pulse (Bitcraze locodeck.c does it first).

Fix:
- hwdef (`crazyflie2/hwdef.dat`): commented out the USART3 `PC10/PC11` lines and
  removed USART3 from `SERIAL_ORDER`; added
  `PC10 DW1000_RESET INPUT PULLUP GPIO(1)` and
  `PC11 DW1000_IRQ INPUT PULLDOWN GPIO(2)`.
  NOTE: removing USART3 from SERIAL_ORDER SHIFTS indices — USART6 (nRF radio) is
  now SERIAL1 and USART2 is SERIAL2 (were 2 and 3). Use `EMPTY` in SERIAL_ORDER
  instead if you need to preserve the old SERIALn numbering.
  `EMPTY` preserves SERIALn but does NOT preserve MAVLINK_COMM_n — see below.

## SERIALn is not MAVLINK_COMM_n (the channel-index shift)

`GCS::setup_uarts()` walks MAVLink *protocol instances* via
`AP_SerialManager::find_serial()`, so a port only consumes a COMM index if its
`SERIALn_PROTOCOL` is a MAVLink variant. An `EMPTY` slot has no
`SERIALn_PROTOCOL` param at all (the hwdef generator emits `HAL_HAVE_SERIALn 0`,
so AP_SerialManager's `var_info[]` omits it and `state[n].protocol` reads back as
0 = Console, which `protocol_match()` does not accept as MAVLink). The EMPTY slot
is therefore skipped and every later port shifts DOWN one COMM index:

| SERIALn | port   | role         | before      | after       |
|---------|--------|--------------|-------------|-------------|
| SERIAL0 | OTG1   | USB console  | COMM_0      | COMM_0      |
| SERIAL1 | EMPTY  | (was USART3) | COMM_1      | skipped     |
| SERIAL2 | USART6 | nRF51 radio  | COMM_2      | **COMM_1**  |
| SERIAL3 | USART2 | deck TX2/RX2 | COMM_3      | **COMM_2**  |

All the `if (chan == MAVLINK_COMM_x)` guards in GCS_Common.cpp / GCS_MAVLink.cpp
/ RadioBuffer.cpp now go through the named aliases `CF_CHAN_NRF` and
`CF_CHAN_AIDECK`, defined once in `GCS_MAVLink.h` under `HAL_CF21`. Change
SERIAL_ORDER again -> update those two defines only.

Also note the generated `hwdef.h` is only regenerated by `./waf configure`, not
by `./waf copter`. After editing `hwdef.dat`, re-run configure or the build will
silently keep the OLD serial layout.
- backend: `init_device()` pulses RSTn before any SPI access — drive
  `HAL_DW1000_RESET_PIN` (=GPIO(1)) low ~2ms, then release to INPUT (never drive
  high; external pull-up brings it up), wait ~5ms for the chip to reach IDLE.
  `HAL_DW1000_RESET_PIN`/`HAL_DW1000_IRQ_PIN` in AP_Ranging_DW1000.h must match
  the hwdef `GPIO(n)` numbers.

`locodeck.c` (Bitcraze deck driver) is kept as `locodeck.c.reference` — renamed
so the library build does NOT try to compile it (it needs Crazyflie firmware
headers: stm32fxxx.h, FreeRTOS, deck.h). Reference only.

## libdw1000 submodule

- Path: `modules/libdw1000` (upstream https://github.com/bitcraze/libdw1000.git,
  Apache-2.0, one-way compatible into ArduPilot GPLv3). Portable C driver.
- Headers in `inc/`, sources `src/libdw1000.c` + `src/libdw1000Spi.c`.
- Update to latest upstream: `git submodule update --remote modules/libdw1000`.
- **Do NOT** `git submodule update --init --recursive` on it: its nested
  `vendor/unity` + `vendor/cmock` are test-only frameworks we don't build.

## waf build integration (done)

- `modules/libdw1000/wscript` — `bld.stlib(target='libdw1000', ...)` compiles
  `src/*.c` into `liblibdw1000.a`, `export_includes=['inc']`. (test/ & vendor/

    ArduPilot's `ap_library` mechanism and only resolves dirs under

## DW1000 backend (`AP_Ranging_DW1000.{h,cpp}`)

- Includes the submodule via `extern "C" { #include <libdw1000.h> }`.
- Implements the 5 `dwOps_t` callbacks against `hal.spi`:
  - `spiRead`  -> `Device::transfer(header, hlen, data, dlen)` (single CS)
  - `spiWrite` -> concat header+payload into `_tx_scratch`, one CS transfer
  - `spiSetSpeed` -> maps `dwSpiSpeedHigh/Low` to `SPEED_HIGH/LOW`
  - `delayms` -> `hal.scheduler->delay()`
  - `reset` -> `_ops.reset=nullptr` (libdw1000 uses SPI soft-reset); stub
    ready if a reset GPIO is wired later.
- C callbacks recover the instance via `dwSetUserdata`/`dwGetUserdata`.
- Ops assume the bus semaphore is already held: `init_device()` holds it around
  `dwGetDeviceId`/`dwConfigure`; the periodic `timer()` runs on the bus thread.
- Binds SPI device `"dw1000"` — must match the SPIDEV entry in
  `crazyflie2/hwdef.dat` (low 2MHz / high 20MHz = dwSpiSpeedLow/High).
- Verifies chip id `0xDECA0130`.

## Milestone B

### B1 — radio link test (done)
- RF config in `configure_radio()` mirrors locodeck.c: `MODE_SHORTDATA_FAST_ACCURACY`,
  `CHANNEL_2`, `PREAMBLE_CODE_64MHZ_9`, smart power, antenna delay 0.
- Event handling by POLLING, not IRQ: `timer()` (bus thread, 1kHz) calls
  `service_radio()` -> `dwHandleInterrupt()`, which reads the DW1000 status
  register over SPI and dispatches to the attached handlers. No hardware
  interrupt is used (PC11/IRQ is wired but not required). DS-TWR accuracy is
  unaffected because ranges come from the chip's hardware timestamps.
- Behaviour: each node broadcasts a 3-byte heartbeat `[type,src,seq]` at 5Hz and
  listens permanently; on RX it counts + records src/seq/power and reports once a
  second: `DW1000 link: rx=.. last src=.. seq=.. pwr=..dBm`.
- New param `RNG_NODE_ID` = this node's address (set differently per aircraft).
  Backend reads it via `AP_Ranging_Backend::get_node_id()` (friendship is not
  inherited, so the subclass can't touch `_frontend._node_id` directly).
- New param `RNG_DEBUG` (0=off, default) gates verbose output at RUNTIME (no
  reflash). The periodic link report only prints when `get_debug() > 0`. Init
  detection messages + errors stay unconditional (one-shot, always useful).
  Set `RNG_DEBUG=1` to watch the link counters during the B1 test.

Test: flash both craft, `RNG_TYPE=1` on both, `RNG_NODE_ID=1` and `=2`. Each
should report `rx=` climbing => bidirectional RF link + event path confirmed.

Link/TX health counters (bus thread only, reported in the GCS line):
- `_rx_count` received, `_rx_timeout` RX timeouts, `_rx_failed` CRC/PHY errors.
  NOTE: `_rx_timeout` stays 0 in B1 (permanent receive, no RX wait-timeout set);
  it becomes meaningful in B2 where the exchange arms RX with a timeout.
- TX watchdog: `send_heartbeat()` marks `_tx_in_progress`; `handle_sent()` clears
  it (`_tx_done++`). If the sent event never arrives within `TX_TIMEOUT_MS`,
  `timer()` counts `_tx_fail++` and re-arms RX — without this a stuck transmit
  would leave the radio permanently deaf (RX is only re-armed in handle_sent).
- The event handlers are `static`, so they MUST touch counters via the
  recovered instance (`b->_rx_timeout++`), never bare members.

### B2 — Alternative DS-TWR exchange (done, untested on HW)
Implements Decawave APS013 eq.17: `Tf = (Ra*Rb - Da*Db)/(Ra+Da+Rb+Db)` (tolerates
asymmetric reply delays). B1 heartbeat replaced by the exchange; link counters kept.

- **Topology**: every node round-robin-polls all neighbours (ids `0..RNG_NUM_NODES-1`
  skipping self, one poll per `POLL_PERIOD_MS`) AND responds to incoming polls. In
  3-msg DS-TWR the RESPONDER holds all 6 timestamps and computes the range, so a
  node's ranges come from *responding* to neighbours' polls -> NO report-back.
- **New param** `RNG_NUM_NODES` (default 2). Assumes contiguous ids from 0.
- **One exchange at a time** (single half-duplex radio): `State` = IDLE /
  I_WAIT_RESP / I_SENDING_FINAL / R_WAIT_FINAL. Anything arriving mid-exchange or
  not addressed to us is dropped; stalls recover via `EXCHANGE_TIMEOUT_MS` +
  retry-next-round. (A concurrent multi-exchange design w/ a circular buffer is a
  future throughput optimization; not needed for a few nodes on one radio.)
- **Delayed TX** for all 3 frames via `dwSetDelay()` (needs TX_MODE from
  `dwNewTransmit` first; returns the antenna-delay-corrected tx timestamp we
  embed). `wait4resp(true)` on POLL/RESPONSE auto-arms RX for the reply;
  `wait4resp(false)` on FINAL, then `handle_sent` resumes listening.
- **Frames**: `[type,src,dst,seq]`; FINAL appends poll_tx/resp_rx/final_tx
  (3x 40-bit LE). Timestamps are 40-bit; all diffs masked `& 0xFFFFFFFFFF`;
  products in uint64, numerator in int64; `distance = Tf_ticks * DISTANCE_OF_RADIO`.
- **Reply delay** `REPLY_DELAY_US=3000` (~1.9e8 ticks) - must exceed the ~1ms poll
  latency; large delays are fine for alt DS-TWR and are why we chose it.
- Ranges published via `set_node_distance(peer, dist)`; `_last_update_ms` set on
  success so `healthy()`/per-node health reflect live ranging.

Tunables to revisit on HW: POLL_PERIOD_MS, REPLY_DELAY_US, EXCHANGE_TIMEOUT_MS,
range sanity gate.

#### RX fix — IRQ-gated servicing (CRITICAL; debugged on B1, ported to B2)
Symptom on HW: `rx=0`, `fail` climbing, `sys=0xFFFFFFFF`. Root cause: **blindly
polling `dwHandleInterrupt()` at 1kHz** hammered SYS_STATUS (incl. mid-reception),
returning intermittent `0xFFFFFFFF` ("SPI busy/unresponsive") and wrecking RX.
Fix (matches Bitcraze's event model):
- `configure_radio()` enables the chip's interrupt outputs
  (`dwInterruptOnSent/Received/ReceiveFailed/ReceiveTimeout` + a
  `dwWriteSystemEventMaskRegister` flush) - `dwConfigure` had cleared the mask.
- `service_radio()` calls `dwHandleInterrupt()` ONLY when
  `hal.gpio->read(HAL_DW1000_IRQ_PIN)` is high - polled flag, NOT a hardware ISR.
- hwdef: `PC11 DW1000_IRQ ... GPIO(60)`, `PC10 DW1000_RESET ... GPIO(61)`,
  USART3 commented, `SERIAL_ORDER OTG1 EMPTY USART6 USART2`. Header
  `HAL_DW1000_IRQ_PIN=60`/`RESET_PIN=61` MUST match those GPIO() numbers.
  (Low numbers like GPIO(1)/(2) aren't fatal but are unconventional; keep 60/61.)
Result on B1: `good=ok=irq` climbing at the peer's TX rate, zero failures,
`sys=0x0`. Bidirectional confirmed. Verified fix is REQUIRED for any RX to work.

B2 still needs HW ranging validation (needs 2 radios).

#### Poll jitter — mutual-poll livelock fix (HW-found)
Symptom: DS-TWR produced a few ranges then `rng` froze while `xfail` climbed at
the full poll rate (~20/s) with `rx`/`tx`/`irq` healthy. Cause: both nodes poll
on the SAME fixed `POLL_PERIOD_MS` and boot in phase, so each sends a POLL while
the other is mid-poll (not IDLE) -> both DROP the incoming POLL -> both time out
-> both re-poll in lockstep, forever. Deterministic livelock (that's why rng
freezes rather than climbing slowly).
Fix: jitter the initiator interval - `_poll_interval = POLL_PERIOD_MS +
get_random16() % POLL_JITTER_MS` (50-100ms), so the two nodes drift out of phase
and one is usually IDLE when the other polls. (A further improvement, if needed:
let an initiator abandon its own poll to answer an incoming POLL, instead of
dropping it - not done yet.)

### Exposed parameters (RNG_)
All read via `AP_Ranging_Backend::get_*()` accessors (friendship isn't inherited).
- `RNG_TYPE`, `RNG_NODE_ID`, `RNG_DEBUG` (0/1/2=listen-only), `RNG_NUM_NODES`.
- `RNG_ANT_DLY` (default 16384) — antenna-delay calibration; applied in
  `configure_radio()` before `dwCommitConfiguration` writes TX_ANTD/LDE_RXANTD.
  Higher = shorter reported range. REBOOT-required. (0 gave the ~155m offset.)
- `RNG_POLL_MS` (50), `RNG_REPLY_US` (3000), `RNG_XCHG_MS` (30) — read LIVE each
  cycle (no reboot); reply-us -> ticks via `reply_delay_ticks()`.
- `RNG_CHAN` (2) — UWB channel; RF config so REBOOT-required; all nodes must match.

## TWR log message (per-node)

The `TWR` log carries 4 fixed slots, each self-describing:
`TimeUS, Cnt, Hlth, ID0..ID3, D0..D3`.
- `IDn` = node id in slot n (0 if unused); `Dn` = that node's last measured range.
- `Hlth` = per-node health BITMASK (bit n set => slot n has a recent range,
  i.e. `node_healthy(n)`). Overall health is `Hlth != 0`.
- `Dn` is the RAW last range (not zeroed when stale) - gate on the `Hlth` bit.
- **Stable ordering**: `set_node_distance(node_id, dist)` keys on node id and
  assigns each id a fixed slot on first sight, never reassigning, so column n
  always refers to the same node across log records. This also finally
  populates `NodeState.id` (previously never set).
- Node ids are logged as uint8 (RNG_NODE_ID is 0..255). Widen the log fields to
  `H` if addressing ever exceeds 255.
- log() fills local arrays then assigns the packed struct BY VALUE - never take
  the address of a packed float member (-Waddress-of-packed-member / unaligned).

## Design notes

- Transport lives in the **backend**, not the base class (DW1000 = SPI, unlike
  AP_Beacon's UART-only backends). The base is transport-agnostic.
- `NodeState` = `{id, healthy, distance, distance_update_ms}` — no position;
  a peer's location is unknown (it's what a downstream estimator would solve).
- `node_healthy()` enforces `AP_RANGING_TIMEOUT_MS`, so stale nodes auto-drop.
- `AP_RANGING_MAX_NODES` (default 4) caps tracked peers; bump for larger swarms.

## Building / compile check

- The real target is `crazyflie2` (ARM) — needs `arm-none-eabi-gcc`.
  `./waf configure --board crazyflie2 && ./waf copter`
- Without the ARM toolchain, a SITL copter build exercises the same AP_HAL API:
  `./waf configure --board sitl && ./waf copter`
- Python build deps required: `empy==3.3.4 pymavlink pexpect future dronecan
  intelhex` (waf reports each missing one and aborts before compiling).
- ACTIVATE the venv before building (`source .venv/bin/activate && ./waf copter`),
  don't just call `.venv/bin/python ./waf`. The final `make_intel_hex.py` step
  runs via shebang `#!/usr/bin/env python3`, which picks the first `python3` on
  PATH; without activation that's the system python (no `intelhex`) and only the
  `arducopter_with_bl.hex` step fails (the .apj/.bin are already built).
